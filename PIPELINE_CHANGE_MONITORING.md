# Tender hierarchy and change monitoring

Implemented without changing authentication, navigation, worksheet layout, or Excel import headers. Existing ten imported records are retained; older stored source snapshots are migrated deterministically, without re-running Agent 2 or a full Agent 3 analysis.

1. **Auction root cause:** normalization previously read only tender-level `auctionPeriod`. It now falls back to source lot auctions and retains individual lot dates.
2. **Hierarchy:** `tender-hierarchy.ts`, `prozorro.server.ts`, and `preparation.server.ts` collect source customer code, lots, items, documents, questions/answers, and available revisions. Raw structured responses remain separate from merged presentation data; changes also retain previous source snapshots.
3. **Aggregation:** one row per tender. Tender expected value has priority; homogeneous numeric lot values can be summed when the tender total is absent. Different currencies or cancelled lots prevent summation. Mixed units are never added. Different auctions, delivery periods, submission periods and addresses have compact indicators and source details. Imported exact values remain locked.
4. **Q&A:** read embedded source questions, or the public `/questions` endpoint when omitted. Preserve source text, question/answer timestamps and lot relation. Card tab “Звернення” separates participant claims from buyer answers. Classification requires a cited source; participant wording alone cannot establish impact.
5. **Documentation verification:** buyer promises are insufficient. Verification references actual document registry entries: earlier/later versions of a logical document, or a dated file explicitly recording documentation changes. This verifies publication, not the participant’s allegations or the legal adequacy of changes. Original bytes, SHA256, source checksum, metadata, cached version identifiers and extracted text are retained. Old versions are not overwritten. Deterministic text differences feed delta analysis; unavailable text blocks unsupported analysis.
6. **Fingerprints:** `structuredDataHash`, `lotsHash`, `itemsHash`, `documentsHash`, `questionsHash`, `answersHash`. Stable key/record ordering prevents reanalysis due to harmless reordering. Document fingerprints include registry metadata, source checksum and cached content hash.
7. **Branches:** structured changes update final data immediately, without GPT. Semantic changes run Agent 3 with changed fragments, old relevant requirements, Q&A and document references. At most one targeted document reread follows. Results are extractively verified before merging. Lifecycle changes use deterministic Agent 4 rules, independently of Agent 3 success. Public winner data does not establish our victory. API attempts and token usage are audited, including retries/failures.
8. **Unchanged source:** zero Agent 3 calls, zero Agent 4 calls, zero AI tokens. ADMIN → AI Агенти → Crash test / Pipeline → tender → “Перевірити зміни зараз” uses the same checker. Per-record debug shows schedule, fingerprints, lot/Q&A counts, reasons, scope, usage, errors, original agent results, delta results and raw source history.
9. **Actual case `UA-2026-10-05-010567-a`:** source has one lot, two items, auction `2026-10-21T12:30:03.758+03:00`, three answered questions and six documents (five parsed; signature `sign.p7s` is unsupported). Registry includes the amendment protocol and documentation amendments published 06.10.2026 at 12:28. The initial Q&A delta plus one targeted reread used two real API requests / 13,619 tokens. Repeated source checks and the browser ADMIN action used zero AI requests/tokens. All ten real imported records remain. Browser verified table/detailed auction, card Q&A and ADMIN diagnostics.
10. **Validation:** TypeScript and production build pass; 129/129 tests pass. Existing ExcelJS client chunk remains above the bundler warning threshold. No deployment was created.

## Runtime scope

The application server starts an unref’d watcher timer when authenticated crash storage initializes. Cadence is configurable in `defaultWatchCadence`: 3 hours active, 1 hour within 24 hours of submission deadline, 12 hours after submission, off for completed/cancelled/unsuccessful procedures. A lightweight minute tick selects only due records; shared pipeline locks prevent overlap. Error checks reschedule instead of repeatedly querying every minute. Open tabs refresh saved merged records every 30 seconds.

This local MVP watcher requires a running server and the existing local storage. The timer and local file storage are not a durable scheduler/database on serverless Vercel. Production scheduling and durable storage are separate deployment work; no Vercel deployment or scheduler was provisioned here.
